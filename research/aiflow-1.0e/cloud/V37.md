# V36 진단과 V37 closest-rival 재현

[기본 Linux CPU 설치](README.md)를 먼저 완료한다. 연구 작업 디렉터리는 `research/aiflow-1.0e/selective-2d`이며 Torch 2.5.1+cpu, NumPy 2.1.3, Python 3.12를 사용한다. 원본 아카이브와 V35 인증서를 보존한다.

V36은 이미 완료된 V35 대조군의 2,304-step AdamW 상태에서 마지막 96단계를 재생했다. 96개 전체 기록과 최종 가중치의 비트 일치를 요구한다. 같은 fitted TRAIN 8배치의 잔여 오류를 진단했으며 새 평가 데이터나 계수 탐색은 사용하지 않았다. [V36 결과](../selective-2d/reports/ADAM_MARGIN_REPLAY_V36_20261006.md)

V37은 두 조건에서 전체 64행 CE와 feature 보존을 유지한다. 후보는 교사 정답 행마다 학생의 가장 높은 비정답 logit 클래스를 선택해 교사 대비 감소한 gap의 제곱을 보정한다. 동률은 클래스 인덱스가 작은 쪽을 선택한다. 정규화 분모도 기존 Top-5 union pair 수에서 교사 정답 행 수로 바뀐다. 같은 계수여도 gradient 크기가 같다는 뜻은 아니다.

아래 출력 경로는 **새 재현 실행**에만 사용한다. 실제 완료 결과나 진행 중 디렉터리를 덮어쓰지 않는다. `prepare`가 봉인한 소스·계수·진단 파일을 실행 중 수정하지 않는다. 새 실행도 완료된 V35 대조군과 2,400개 전체 기록 및 최종 57개 파라미터 텐서가 비트 일치해야 한다.

```bash
experiment=artifacts/hwr_closest_rival_new_run
python scripts/run_hwr_closest_rival_v37.py prepare --output "$experiment"
python scripts/run_hwr_closest_rival_v37.py train --output "$experiment" --arm v33_control &
control_pid=$!
python scripts/run_hwr_closest_rival_v37.py train --output "$experiment" --arm closest_rival &
challenger_pid=$!
wait "$control_pid"
control_status=$?
wait "$challenger_pid"
challenger_status=$?
test "$control_status" -eq 0 && test "$challenger_status" -eq 0
```

두 종료 코드와 두 `completed.json` 모두 정상인 경우에만 아래 단계를 실행한다. 각 arm은 2 Torch thread를 사용한다. 관찰한 4-core 제한에서 전체 학습은 약 40분이다.

```bash
python scripts/run_hwr_closest_rival_v37.py evaluate --output "$experiment"
python scripts/verify_hwr_closest_rival_v37.py --output "$experiment"
python scripts/audit_hwr_closest_rival_v37.py --output "$experiment"
```

학습·평가 구현은 수정하지 않은 V35 함수에 프로세스 안에서만 설정을 연결해 재사용한다. 따라서 체크포인트·평가 JSON 컨테이너에는 기존 V35 schema가 남아 있다. 실험은 V37 `frozen_plan.json`, arm 이름과 별도 V37 인증서로 식별한다. 이 재사용은 이전 파일을 변경하지 않는다.

TRAIN 진단의 `arm_gap`은 조건별 목적함수 값이다. `common_near_gap`은 두 조건 모두 기존 gap 정의로 계산해 함께 비교한다. fitted TRAIN의 512개 노출에서 gradient를 관찰하며 추가 optimizer step은 없다.

149식 평가는 반복 관찰한 정답 grouping 제공 HWR 진단이다. 새 acceptance나 전체 raw-stroke 수식 인식 정확도는 아니다. owned/CROHME 데이터는 optimizer에 들어가지 않는다. 학습 도중 평가, epoch 선택, 제품 채택이나 배포를 하지 않는다. 프로세스는 새 클라우드 작업에 승계되지 않는다.

## 중단된 V37 실행 복구

2026-10-07(한국 시간)에 별도 복구 CLI를 추가했다. 원래 trainer와 봉인된 V37 소스는 변경하지 않는다. 두 원래 프로세스가 종료된 것을 먼저 확인한다. 아래는 아직 복구를 시도하지 않은 중단 arm 하나를 재개하는 명령이다.

```bash
python scripts/resume_hwr_closest_rival_v37.py prepare --output "$experiment" --arm v33_control
python scripts/resume_hwr_closest_rival_v37.py resume --output "$experiment" --arm v33_control
```

다른 arm에는 `--arm closest_rival`을 사용한다. 준비 단계는 원래 `resume_state.pt`, 전체 중단 로그와 `run_started.json`을 `recovery_20261007/`에 바이트 그대로 복사하고 새 복구 코드의 SHA를 봉인한다. Resume은 모델·AdamW·Torch RNG를 복원하고, 저장 상태 이후 이미 기록된 구간의 **전체 직렬화 기록**이 비트 일치하는지 검사한다. 겹치는 구간은 다시 로그에 쓰지 않고, 처음 실행하는 후속 step만 덧붙인다. 복구 실패도 증거 디렉터리에 남기며 기존 실행을 덮어쓰거나 새 optimizer를 적용하지 않는다.

각 arm의 최종 학습 궤적은 여전히 2,400단계다. 재생한 겹침은 추가 계산이므로 `executed_updates_this_process`, `overlap_replayed_steps`, `new_logged_steps`를 구분해 기록한다. 독립 검증은 보존 입력의 해시·원래 로그 prefix·step 회계를 확인하고, 전체 대조군의 최종 가중치와 2,400개 기록을 이전 완료 대조군과 비교한다. 복구 구간을 독립 검증기가 다시 forward한 것은 아니다.
